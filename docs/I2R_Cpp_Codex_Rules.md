# I2R C++ Codex 详细规则库

## 0. 定位

本文档供 Codex / 代码代理读取，用于约束本仓库 C++ 代码生成、修改、重构和补注释行为。

本文档不是教程，不解释背景。执行时以规则为准。

## 1. 总体执行原则

### 1.1 适用范围

适用于：

- `.h` / `.cpp` 文件；
- 类、结构体、函数、变量、枚举、联合体、typedef、命名空间；
- 文件头注释、类注释、函数注释、实现注释、TODO/FIXME；
- 新增代码、修复代码、重构代码、补注释代码。

### 1.2 规则优先级

发生冲突时：

1. 用户当前明确要求优先。
2. 更近层级 `AGENTS.md` 优先。
3. 当前文件已有局部风格优先。
4. 本规则库优先于一般习惯。
5. 不确定时，减少改动范围，保持旧代码稳定。

### 1.3 修改范围

必须：

- 只改任务相关代码。
- 保持接口兼容，除非任务明确要求改接口。
- 修改接口时同步修改声明、定义、调用点和注释。
- 删除或修正已经失效的注释。

禁止：

- 无关格式化。
- 无关重命名。
- 全文件大范围重排。
- 借机统一历史风格。
- 引入与任务无关的新库、新框架、新抽象层。

## 2. 文件与目录

### 2.1 文件后缀

- 头文件使用 `.h`。
- 源文件使用 `.cpp`。
- 不新增 `.hpp`、`.cc`、`.cxx`，除非当前模块已有明确约定。

### 2.2 文件命名

必须：

- 文件名使用英文单词组合。
- 每个单词首字母大写。
- 单词之间不加 `_` 或 `-`。
- 文件与具体类强关联时，文件名与类名一致。

示例：

```text
File.h              正确
ThreadPool.cpp      正确
file.h              错误
Thread_Pool.cpp     错误
```

### 2.3 目录组织

独立模块优先采用：

```text
ModuleName/
├── include/
│   └── ModuleName/
│       └── PublicHeader.h
└── source/
    ├── PrivateHeader.h
    └── Implementation.cpp
```

规则：

- public 头文件放 `include`。
- `.cpp` 和私有头文件放 `source`。
- 不把实现细节暴露到 public include。

## 3. 头文件与源文件结构

### 3.1 头文件结构

头文件顺序：

1. 文件头注释。
2. include guard。
3. include。
4. 前置声明。
5. 命名空间。
6. 常量、类型、类、函数声明。
7. include guard 结束注释。

### 3.2 include guard

必须使用 include guard。

宏命名格式：

```text
<PROJECT>_<PATH>_<FILE>_H
```

示例：

```cpp
#ifndef FOO_BAR_BAZ_H
#define FOO_BAR_BAZ_H

// declarations

#endif // FOO_BAR_BAZ_H
```

禁止：

```cpp
#ifndef HEADER_H
#define HEADER_H
```

### 3.3 include 顺序

`.cpp` 文件 include 顺序：

1. 当前 `.cpp` 对应的主头文件。
2. C 标准库。
3. C++ 标准库。
4. 第三方库。
5. 项目内部头文件。

项目内部头文件尽量按目录结构和字母顺序排列。

禁止：

- 无必要的 `../`。
- 无必要的 `./`。
- 为了省事引入巨型头文件。
- 在头文件中引入本可前置声明的重依赖。

### 3.4 源文件结构

源文件顺序：

1. 文件头注释。
2. 主头文件 include。
3. 其他 include。
4. 匿名命名空间或文件内辅助定义。
5. 函数/类成员函数实现。

## 4. 版式与格式

### 4.1 缩进

- 使用 4 个空格缩进。
- 禁止 Tab 缩进。
- 折行后增加一层缩进，或与首个参数/操作数对齐。

### 4.2 空行

必须加空行：

- 每个类声明之后。
- 每个函数定义之后。
- 逻辑段落之间。
- 变量声明区与主要执行逻辑之间。
- `if` / `for` / `while` / `do while` 语句前后，视上下文保持清晰。

禁止：

- 注释和被注释代码之间插入空行。
- 过多连续空行。

### 4.3 空格

必须加空格：

- 关键字之后：`if (`、`for (`、`while (`。
- `,`、`;` 后面，除非位于行尾。
- 二元操作符两侧：`=`, `+=`, `==`, `>=`, `+`, `*`, `%`, `&&`, `||`, `<<`。
- 类型和变量名之间。

禁止加空格：

- 函数名和 `(` 之间。
- `(` 之后、`)` 之前。
- `[]`、`.`、`->`、`::` 两侧。
- 一元操作符与操作数之间：`!flag`、`++i`、`--i`。

指针/引用声明按当前文件风格；新增代码默认让 `*` / `&` 靠近变量名：

```cpp
int *ptr;
const CString &name;
```

### 4.4 大括号

默认规则：

- `{` 和 `}` 独占一行。
- 与控制语句左对齐。
- 嵌套块按 4 空格缩进。

示例：

```cpp
if (condition)
{
    DoSomething();
}
else
{
    DoOtherThing();
}
```

例外：如果当前文件长期使用同一行括号风格，修改局部代码时保持局部一致，不主动全文件切换。

### 4.5 行宽与折行

- 代码行尽量控制在 80 字符左右。
- 过长表达式在低优先级操作符处折行。
- 折行后的操作符可放在新行行首，以突出逻辑关系。
- 长函数调用可每行一个参数。

## 5. 命名规则

### 5.1 共性规则

必须：

- 使用可读英文单词。
- 名称能表达职责或语义。
- 类型和变量使用名词或名词短语。
- 函数使用动词或动宾短语。

禁止：

- 只靠大小写区分两个名称。
- 无意义数字编号，例如 `Value1`、`Value2`，除非业务确实需要序号。
- 拼音和英文混用，除非现有模块已有强约定。
- 随意缩写，尤其是不常见缩写。

### 5.2 变量

普通变量和参数：

```cpp
int referenceCount;
```

规则：

- 小写字母开头。
- 后续单词首字母大写。
- 不使用下划线。

静态变量：

```cpp
static int s_initValue;
```

全局变量：

```cpp
int g_initValue;
```

成员变量：

```cpp
int m_width;
int m_height;
```

规则：

- 静态变量加 `s_`。
- 全局变量加 `g_`。
- 类成员变量加 `m_`。
- 不主动引入全局变量；确需新增时必须说明理由并限制作用域。

### 5.3 类、结构体、接口、模板

普通类/结构体：

```cpp
class CFoo;
struct CFooData;
```

接口类：

```cpp
class IFoo;
```

模板类：

```cpp
template<class T>
class TFoo;
```

规则：

- 普通类以 `C` 开头。
- 接口类以 `I` 开头。
- 模板类以 `T` 开头。
- 结构体和类命名保持统一。
- 修改既有代码时，不主动把历史类名改成现代风格。

### 5.4 函数

普通函数：

- 使用动词或动宾短语。
- 多个单词组合时，按当前模块风格使用首字母大写或小写开头形式。
- 存取函数与变量匹配：`getXXX()` / `setXXX()`。

函数声明和定义中的形参名必须一致。

### 5.5 常量、枚举、联合体、typedef、命名空间

常量：

```cpp
const int MAX_BUFFER_SIZE = 4096;
```

枚举类型：

```cpp
enum EType
{
    INT = 0,
    STRING = 1,
};
```

联合体：

```cpp
union UMultiType
{
    double dValue;
    int iValue;
};
```

typedef：

```cpp
typedef CFooIterator IteratorT;
```

命名空间：

```cpp
namespace scut_irr_sontech
{
}
```

规则：

- 常量全大写，单词间用 `_`。
- 枚举类型以 `E` 开头。
- 枚举值全大写，单词间用 `_`。
- 联合体类型以 `U` 开头。
- typedef 名以 `T` 结尾。
- 命名空间全小写，可用 `_` 连接。

## 6. 注释规则

### 6.1 总原则

注释写：

- 职责。
- 边界。
- 所有权。
- 生命周期。
- 线程/锁约束。
- 调用时机。
- 副作用。
- 算法原因。
- 历史兼容原因。

注释不写：

- 显而易见的代码翻译。
- 情绪化内容。
- 吐槽。
- 空模板。
- 与代码不一致的旧说明。

### 6.2 文件头注释

新建重要 `.h` / `.cpp` 文件时，文件头只保留有价值信息：

- `@file`
- `@brief`
- `@details`
- `@author`
- `@version`

示例：

```cpp
/**
 * @file      VISManager.h
 * @brief     统一管理可视对象并按脏标记触发增量刷新。
 * @details   本文件定义 RobotSimVIS 的可视对象管理器单例。
 *            该类不拥有可视对象生命周期，只负责注册表维护和刷新调度。
 * @author    I2R Laboratory
 * @version   1.0
 */
```

禁止：

```cpp
/**
 * @file
 * @brief
 * @details
 */
```

### 6.3 类注释

以下类必须写注释：

- 跨模块公共类。
- 单例类。
- 抽象基类/接口类。
- 生命周期复杂的类。
- 线程语义复杂的类。
- 模板类。
- 通知/回调/观察者相关类。

类注释至少说明：

- 类职责。
- 所属层次。
- 所有权边界。
- 线程、刷新或调用时机约束。

推荐：

```cpp
/**
 * @brief 机器人状态缓存对象。
 *
 * 该类位于通信层和控制层之间，只保存最近一次从控制柜接收的状态帧。
 * 本类不负责 TCP 接收，也不负责机器人运动控制。
 *
 * 所有权：由通信模块创建并持有。
 * 线程约束：写入发生在通信线程，读取发生在控制线程，访问前必须持有外部互斥锁。
 */
class CRobotStateCache
{
};
```

禁止只写：

```cpp
// 管理类
// 工具类
// 这是一个重要的类
```

### 6.4 函数注释

必须写注释的函数：

- 公共接口。
- 虚函数/重写函数。
- 跨线程调用函数。
- 生命周期管理函数。
- 具有副作用的 setter。
- 非直观算法函数。
- 涉及锁、缓存、状态机、通信协议、坐标变换、视觉算法的函数。

可以不写注释：

- 简单 getter。
- 一眼可读的短小局部函数。
- 空实现或显然的构造/析构函数。

函数注释重点：

- 做什么。
- 输入/输出是什么。
- 是否立即生效。
- 是否有副作用。
- 是否有线程/锁要求。
- 参数是否允许 `NULL`。
- 返回值所有权归属。

示例：

```cpp
/**
 * @brief 根据最新状态帧计算下一目标位姿。
 *
 * @param currentPose 当前机器人末端位姿，单位为控制柜内部脉冲或工程约定单位。
 * @param featureError 图像特征误差，单位为像素。
 * @param nextPose 输出的下一目标位姿。
 * @return true 表示成功生成目标位姿；false 表示当前状态不满足控制条件。
 *
 * 线程约束：只能在控制线程调用。
 * 副作用：会更新内部 ACK 计数。
 */
bool CalculateNextPose(const long currentPose[6],
                       const CFeatureError& featureError,
                       long nextPose[6]);
```

### 6.5 实现注释

内部实现注释重点写“为什么”，不重复“代码做了什么”。

必须写实现注释的情况：

- 算法推导不直观。
- 存在历史兼容逻辑。
- 有线程/锁顺序要求。
- 有性能优化目的。
- 有外部库使用陷阱。
- 有协议字段、坐标系、单位换算。

示例：

```cpp
// 控制柜状态帧可能被 TCP 拆包，因此这里只推进解析游标，不立即清空缓冲区。
ParseFrameFromBuffer(buffer, &cursor);
```

### 6.6 历史迁移注释

迁移旧代码时，允许保留历史迁移注释，但必须说明：

- 来源模块或旧逻辑。
- 保留原因。
- 当前兼容边界。

禁止保留无法验证、无意义的历史说明。

### 6.7 TODO / FIXME

TODO/FIXME 必须包含：

- 责任人。
- 日期。
- 明确事项。
- 验收目标或移除条件。

格式：

```cpp
// TODO(lijia, 2026-05-09): 将临时固定阈值改为配置项；验收目标是支持界面配置并保存到工程文件。
// FIXME(lijia, 2026-05-09): 当前未处理 TCP 半包超时；验收目标是超时后清空异常帧并记录错误码。
```

禁止：

```cpp
// TODO: later
// FIXME
// TODO optimize
```

## 7. 函数与参数设计

### 7.1 函数长度

- 函数应短小、单一职责。
- 函数超过约 40 行时，优先考虑拆分。
- 不为拆分而拆分；拆分后必须提升可读性。

### 7.2 参数规则

必须：

- 参数写完整类型和名称。
- 输入参数在前，输出参数在后。
- 只读指针参数加 `const`。
- 对象输入参数优先用 `const&`。
- 参数数量尽量不超过 5 个。

示例：

```cpp
void SetValue(int width, int height);
float GetValue(void);
```

禁止：

```cpp
void SetValue(int, int);
float GetValue();
```

### 7.3 返回值规则

禁止：

- 返回局部栈变量的指针或引用。
- 返回所有权不清晰的裸指针。
- 忽略错误状态。

必须：

- 明确返回的是值、指针还是引用。
- 必要时在注释中说明所有权和生命周期。

### 7.4 构造函数

构造函数只做轻量初始化。

复杂初始化放到 `Init()` / `Initialize()` 等函数中，原因：

- 构造函数无法直接返回错误码。
- 复杂初始化失败时行为难控。
- 便于分阶段初始化和错误处理。

单参数构造函数默认加 `explicit`，除非确实需要隐式转换。

## 8. 类设计规则

### 8.1 struct 与 class

使用 `struct`：

- 只有数据成员。
- 需要直接访问数据成员。
- 只有简单构造、析构或 `Reset()`。
- STL 仿函数等轻量对象。

其他情况使用 `class`。

### 8.2 访问控制

- 数据成员默认 `private` 或 `protected`。
- 除简单 `struct` 外，不允许公开数据成员。
- 需要访问成员时提供 `getXXX()` / `setXXX()`。
- 不把外部不会调用的方法声明为 `public`。

### 8.3 声明顺序

类中访问区顺序：

1. `public:`
2. `protected:`
3. `private:`

每个访问区内推荐顺序：

1. typedef / enum。
2. 常量。
3. 构造函数。
4. 析构函数。
5. 成员函数/静态成员函数。
6. 成员变量/静态成员变量。

### 8.4 继承

- 优先组合，谨慎继承。
- 默认只使用 `public` 继承。
- 如果类有虚函数，析构函数必须为 `virtual`。
- 尽量避免多重继承。
- 若必须多重继承，最多一个基类包含实现，其余应为接口类。

### 8.5 接口类

接口类应满足：

- 只有纯虚函数和静态函数，析构函数除外。
- 没有非静态数据成员。
- 不需要公开构造函数；如有构造函数，应为 `protected`。

### 8.6 操作符重载

- 不随意重载操作符。
- 语义明确时才允许，例如等价比较。
- 优先使用 `Equal()`、`CopyFrom()` 等具名函数表达复杂语义。
- 禁止重载 `&`。

## 9. 作用域与变量生命周期

### 9.1 命名空间

允许：

```cpp
namespace module_name
{
}
```

禁止：

- 在头文件中使用匿名命名空间。
- 在头文件顶层使用 `using namespace`。
- 向 `std` 命名空间添加声明。

`.cpp` 中可使用匿名命名空间限制文件内符号：

```cpp
namespace
{
int Helper(void)
{
    return 0;
}
}
```

### 9.2 非成员函数和全局函数

- 能放入命名空间就不要裸露在全局命名空间。
- 仅 `.cpp` 内使用的辅助函数，放匿名命名空间或声明为 `static`。
- 非成员函数不应依赖外部可变状态。

### 9.3 局部变量

- 基本类型可在函数开头集中声明，遵守旧项目风格。
- 对象类型尽量在需要时再定义，避免无谓构造。
- 循环中避免重复构造昂贵对象。

### 9.4 全局变量

- 尽量不要新增全局变量。
- 不新增 class 类型全局对象，包括 `string`、`vector` 等。
- 必须共享状态时，优先封装到类、单例或受限命名空间中，并说明生命周期和线程约束。

## 10. 表达式与控制语句

### 10.1 运算符优先级

- 复杂表达式必须加括号明确顺序。
- 避免嵌套赋值表达式。

禁止：

```cpp
d = (a = b + c) + r;
```

### 10.2 if 比较

布尔值：

```cpp
if (flag)
if (!flag)
```

禁止：

```cpp
if (flag == TRUE)
if (flag == 1)
if (flag == FALSE)
if (flag == 0)
```

整型：

```cpp
if (value == 0)
if (value != 0)
```

浮点数：

```cpp
if ((x >= -EPSILON) && (x <= EPSILON))
```

禁止：

```cpp
if (x == 0.0)
if (x != 0.0)
```

指针：

```cpp
if (p == NULL)
if (p != NULL)
```

本仓库历史规范使用 `NULL`。修改旧代码时不要主动批量改为 `nullptr`。若当前模块已经统一使用 `nullptr`，则按当前模块风格执行。

### 10.3 循环

- 不在 `for` 循环体内修改循环控制变量。
- 循环区间优先使用半开半闭：`[0, N)`。
- 大循环中避免把不变判断放在循环体内部。
- 多重循环中，结合数据访问方式和循环次数考虑效率，不机械调换顺序。

### 10.4 switch

- 每个 `case` 末尾必须明确 `break`、`return` 或注释说明 fallthrough。
- 必须保留 `default`。
- 即使无处理，也写：

```cpp
default:
    break;
```

## 11. 语言特性限制

### 11.1 const 和引用

- 输入对象参数优先 `const&`。
- 输出参数优先指针或明确的引用，按当前模块风格。
- 能加 `const` 的成员函数尽量加 `const`。

### 11.2 默认参数

不要新增默认参数，除非当前接口体系明确依赖默认参数。

### 11.3 RTTI

不要新增运行时类型识别逻辑。避免新增 `dynamic_cast`。确需使用时说明设计原因。

### 11.4 stream

历史规范要求避免 C++ stream，优先使用项目已有日志/格式化方式或 C 风格格式化。

不要为了局部输出引入 `<iostream>`。

### 11.5 STL

- 优先沿用当前模块已有容器和基础库。
- 不为小改动引入新的 STL 容器类型或复杂模板依赖。
- 如果当前模块已经广泛使用 STL，则保持局部一致。

### 11.6 sizeof

优先使用：

```cpp
sizeof(variable)
```

少用：

```cpp
sizeof(Type)
```

### 11.7 自增自减

能用前置自增/自减时，优先：

```cpp
++i;
--i;
```

### 11.8 类型转换

禁止新增 C 风格强制类型转换。

使用 C++ 转换：

```cpp
static_cast<T>(value)
const_cast<T>(value)
reinterpret_cast<T>(value)
dynamic_cast<T>(value)
```

限制：

- `static_cast` 用于明确且安全的静态转换。
- `reinterpret_cast` 高风险，尽量不用；必须使用时写明原因。
- `const_cast` 可能破坏 const 语义，必须谨慎。
- `dynamic_cast` 涉及 RTTI，默认避免。

## 12. 术语统一

必须保持全仓术语一致，包括：

- 类名。
- 模块名。
- 文件名。
- 注释中的中英文术语。
- 大小写形式。

规则：

- 不在新代码中混用旧术语和新术语。
- 不确定术语时，先搜索当前仓库已有命名。
- 修改术语时必须同步代码、注释、文档和调用点。

## 13. 禁止项总表

禁止：

- 空 `@brief` / `@details` / `@param` / `@return`。
- 情绪化注释。
- 吐槽式注释。
- 作者字段写环境名。
- 保留生成器模板空行。
- 旧术语和新术语长期混用。
- 显而易见翻译式注释。
- 无责任人、无日期、无验收目标的 TODO/FIXME。
- 无关格式化和无关重命名。
- 头文件中匿名命名空间。
- 头文件顶层 `using namespace`。
- 新增不必要全局变量。
- 返回局部变量指针或引用。
- 新增 C 风格强制类型转换。
- 随意重载操作符。
- 在构造函数中塞复杂初始化逻辑。

## 14. Codex 修改前后检查清单

### 14.1 修改前

检查：

- 当前任务真正要改什么。
- 相关文件是否已有局部风格。
- 是否涉及公共接口、跨线程、生命周期、通信协议、坐标系或视觉算法。
- 是否需要更新声明、定义、调用点、注释、文档。

### 14.2 修改中

检查：

- 是否只改任务相关代码。
- 是否避免了大范围重排。
- 是否避免引入无关依赖。
- 是否保持命名和格式局部一致。
- 是否同步更新失效注释。

### 14.3 修改后

检查：

- 是否可能编译失败。
- include guard 是否唯一。
- include 是否缺失或过多。
- 函数声明和定义参数名是否一致。
- 指针、浮点、布尔比较是否符合规则。
- TODO/FIXME 是否合格。
- 是否留下临时代码、调试输出、死代码。
- 是否需要提醒用户运行编译或测试。

## 15. 推荐给 Codex 的执行口径

当任务较小：

- 优先最小改动。
- 不创建新抽象。
- 不批量整理。

当任务涉及新增模块：

- 先按目录和文件结构规划。
- 再创建头文件和源文件。
- 写清楚文件头、类职责、接口注释。
- 保持 public/private 边界清楚。

当任务涉及修复 bug：

- 先定位根因。
- 只修根因相关代码。
- 不用风格重构掩盖逻辑修改。
- 必要时增加说明性注释，解释历史兼容或边界条件。

当任务涉及补注释：

- 不给所有函数机械补模板。
- 只给公共接口、复杂逻辑、跨线程/生命周期/副作用函数补注释。
- 删除错误注释优先于保留过期注释。
