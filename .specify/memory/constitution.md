# i2r_rlc Constitution

## Core Principles

### I. 围绕明确变化点建立可替换边界

系统 MUST 只在已知或有证据支持的变化点建立模块边界。替代算法、实验策略、
相机或推理运行时等易变外部依赖，以及需要独立比较的实现，MUST 通过小而稳定的
输入、输出、参数、状态和错误语义与调用方交互。调用方 MUST 依赖这些语义契约，
实现选择 SHOULD 集中在配置、组合或管线路由边界。共享领域类型、评估逻辑和实验
基础设施 MUST 避免依赖单个候选实现。单一且稳定的实现不因假设性的未来需求而被
强制接口化。跨模块或跨开发者责任区的契约变化 MUST 在实现前说明影响范围，并在
共同集成前获得相关维护者确认。

理由：工程已经在视觉算法管线、相机设备、数字孪生传输等真实变化点形成边界；
延续这种做法可降低替换和协作成本，同时避免把每个类都抽象为插件。

### II. 统一且可比较的评估

同一能力的基线实现与候选实现 MUST 在相同输入数据、预处理、参数口径、输出语义和
指标定义下评估。比较结果 MUST 至少记录正确性或质量指标、失败与跳过条件；当性能是
优化目标时，还 MUST 记录耗时及相关资源约束。可替换实现 SHOULD 复用契约测试、参数化
测试、离线 replay 或公共评估工具，而不是各自维护不可比较的验证流程。评估设施 MUST
独立于被评估实现；算法选择不得只依据个别样本或主观观感。

理由：本项目的主要价值来自算法重构和实验，只有统一口径才能判断候选方案是等价、
改进还是退化。

### III. 行为保持与渐进式重构

纯重构 MUST 先明确需保持的可观察行为，并用现有测试、回放数据或新增的最小验证建立
基线。迁移 MUST 以可审查、可回退的增量进行；兼容入口与现代入口并存时，映射关系和
退场条件 MUST 明确。任何有意改变输出、容差、状态转换、错误处理或时序的工作 MUST
作为行为变更写入规格与验收标准，不得以“重构”名义隐含引入。高风险控制、通信和
标定路径 MUST 验证跨子系统行为，而非只验证局部函数。进入共同集成分支的变更 MUST
保持逻辑边界清晰，并在合入前记录已完成的验证和仍存风险。

理由：算法整理经常同时触及遗留兼容路径和运行时编排；将行为变化显式化并小步集成，
可防止重构证据、算法改进证据和协作冲突互相混淆。

### IV. 最小充分架构

实现 MUST 优先采用满足当前需求并保留已知变化点的最小设计。接口、工厂、注册表、
适配器、包装层、新包或插件系统只有在提供可替换性、易变依赖隔离、独立评估、明确
校验边界或显著降耦时才可引入。计划中每个新增抽象 MUST 说明什么会变化、什么保持
稳定、解决何种当前问题，以及为何现有直接设计不足。若理由不能由当前需求、现有耦合
或实验计划证明，MUST 保持更简单的结构。不得仅为符合理想化分层而重写已有有效边界。

理由：项目需要的是围绕算法变化的可演进性，而不是以模块数量衡量架构质量。

### V. 实验隔离与可复现

实验实现 MUST 与默认生产路径隔离，并通过显式构建选项、配置或组合点启用；不得静默
改变默认行为。可用于决策的实验 MUST 记录实现标识、数据集或样本范围、关键参数、
构建配置、依赖条件、指标和结果。随机或环境敏感流程 MUST 固定或记录影响复现的种子
与环境信息。原始数据与基准结果不得被实验过程就地覆盖；无法获得所需数据或依赖时，
验证 MUST 明确失败或跳过原因。

理由：隔离和复现使短期实验可以安全迭代，也使协作者能够在另一工作副本中复核算法选择。

## 项目架构约束

- `Camera`、`Localization`、`DigitalTwin`、`Vision`、`RobotComm`、`Control`、`IBVS`
  和 `UI` 是当前 CMake 子系统边界。功能变更 MUST 优先落在拥有该能力的现有子系统；
  新增顶层子系统必须证明其具有独立职责与演化周期。不得重新引入 `core`、
  `infrastructure`、`app`、`robot` 或 `communication` 作为生产模块。
- `Vision` 与 `Control`、`Localization`/`IBVS`/`DigitalTwin` 分属明确主责区域。跨主责区域
  的修改 MUST 说明为何不能在本模块或既有公开契约内完成；共享的 `UI`、`RobotComm`、
  CMake、配置、数据、文档和测试变更 MUST 评估双方影响。
- 视觉、定位与控制算法的公共输入、输出、参数、状态、坐标或物理单位、有效性和失败
  语义 MUST 保持显式。候选算法若实现相同能力，SHOULD 接入同一管线契约或评估适配边界。
- UI、相机缓冲、文件加载、硬件 SDK、RobotSim/数字孪生传输与算法核心之间 MUST 保持
  转换边界；算法核心不得为方便实验而直接依赖 UI、特定硬件生命周期或外部进程所有权。
- `tests/` 是当前项目统一的 CTest、单元、集成、smoke 和离线 replay 入口。新增验证 MUST
  优先复用该目录的测试注册和既有数据口径，不得在个人分支建立不可共享的评估入口。
- 第三方与遗留代码 SHOULD 通过现有适配或兼容边界使用。修改第三方源码或扩大公共依赖
  面积必须有无法在项目边界内解决的明确理由；只读参考工程不得成为生产构建依赖。
- 工作分解 MUST 按行为、能力、依赖或风险形成有意义的结果，不得机械地按文件、类、
  接口或测试文件拆分。

## 变更与验证工作流

规格 MUST 说明目标变化点、模块主责与共享影响、保持不变的行为、范围外事项和可度量成功
标准。涉及算法比较时，还 MUST 说明基线、候选实现、代表性数据、统一指标和接受阈值。

计划在实现前及设计后 MUST 执行 Constitution Check，至少回答：边界是否对应真实变化点；
新增抽象是否必要；是否跨越开发者主责或共享高冲突区域；生产与实验路径是否隔离；评估
是否共享且公平；行为兼容与迁移风险是否有证据覆盖。任何无法满足的 MUST 规则都需要在
Complexity Tracking 中给出理由、更简单方案及拒绝原因，并由相关维护者明确批准。

验证强度 MUST 与行为风险成比例。优先复用 `tests/` 中的 CTest、契约测试、集成测试、
离线 replay 和共享数据样本；当这些证据不能覆盖新增行为、回归风险、算法等价性或高风险
路径时，MUST 补充最小且针对性的验证。不得仅因新增源文件而强制新增测试文件。验证报告
MUST 区分通过、失败与因数据或依赖缺失而跳过的项目。

个人开发分支合入共同集成分支前 MUST 先同步目标分支、解决冲突并完成与改动风险相称的
本地验证。公共类型、状态机、协议、配置格式、线程所有权、CMake 目标或模块依赖冲突不得
机械选择任一版本，MUST 先确认行为语义和双方影响。具体 Git 命令与分支职责以
`docs/collaboration_git_workflow.md` 为准。

## Governance

本 Constitution 是规格、计划、任务拆分、实现和评审的最高项目工程准则。若其他文档或
惯例与此冲突，以本 Constitution 为准；`AGENTS.md` 可补充执行细节，但不得静默改写这些
项目级原则。

`.specify/` 与 `specs/` 中的项目规则、模板和功能设计记录 MUST 纳入版本控制并随代码共同
评审。个人机器安装的 Skill 只提供执行流程，不能替代仓库内已批准的 Constitution 和设计
产物。协作者使用不同 Skill 版本时，最终产物仍 MUST 满足仓库当前 Constitution 与模板。

修订必须提交书面变更，说明受影响原则、迁移影响及同步模板。版本遵循语义化规则：
删除原则或作不兼容重定义时升级 MAJOR；新增原则、章节或实质扩展约束时升级 MINOR；
不改变治理语义的澄清与文字修正升级 PATCH。原始批准日期保持不变。

每份 feature plan MUST 在研究前和设计后检查合规性；实现评审 MUST 核对规格中的保持行为、
统一评估证据、实验隔离、协作影响以及复杂度说明。对 MUST 的临时例外需要相关维护者批准、
记录适用范围与到期或移除条件，并在后续评审中重新确认。
