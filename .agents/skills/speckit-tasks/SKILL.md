## Task Generation Rules

**CRITICAL**: Tasks MUST be organized by user story to enable independent implementation and testing.

**Tests are OPTIONAL**: Only generate test tasks if explicitly requested in the feature specification or if user requests TDD approach.

### Lean Task Granularity Rules

The following rules refine task granularity while preserving the existing
requirements for user-story organization, dependency ordering, checklist
format, and implementation completeness.

Generate the minimum dependency-complete task set needed to implement
the plan.

Tasks MUST represent meaningful engineering outcomes rather than
individual coding operations.

A task MAY:
- create multiple related files;
- modify multiple related files;
- span multiple implementation layers when they belong to one coherent change;
- include implementation and directly related validation;
- perform one coherent migration or replacement step.

When a task affects multiple files, list the relevant file paths in the
task description rather than splitting the work into one task per file.

Do NOT automatically create separate tasks for:
- every file;
- every class;
- every interface;
- every DTO;
- every model;
- every service;
- every repository;
- every controller or endpoint;
- every adapter;
- imports;
- formatting;
- boilerplate;
- obvious cleanup;
- documentation updates that are incidental to implementation;
- one test file per implementation file.

Components such as models, services, interfaces, repositories, endpoints,
and adapters MAY be implemented together in one task when they serve the
same engineering outcome and share the same dependency and validation
boundary.

Prefer approximately:
- 1-4 tasks for small changes;
- 4-8 tasks for ordinary changes;
- 6-12 tasks for substantial refactors or features.

These ranges are guidance, not quotas.

Do NOT create additional work merely to reach a target task count.

If more than 12 tasks appear necessary, reconsider granularity before
emitting the final task list.

Before exceeding 12 tasks:
1. Identify tasks that share the same engineering intent.
2. Identify tasks that share dependencies or validation.
3. Merge implementation steps that form one coherent outcome.
4. Remove speculative, incidental, or unnecessary work.
5. Keep separate tasks only where independent sequencing, rollback,
   ownership, or validation genuinely requires separation.

Merge tasks when they share:
- engineering intent;
- dependency ordering;
- validation method;
- rollback boundary;
- the same user-story outcome.

Do NOT split work solely because implementation crosses architectural
layers.

For example, if a user story requires introducing a new repository
contract, adapting the service, and updating the caller to use that
contract, these MAY form one task when they represent one coherent
migration outcome.

### Testing and Validation

Follow the existing rule that dedicated test tasks are optional.

Do NOT generate a dedicated test task for every implementation task.

When the specification, constitution, or user explicitly requires new
tests, prioritize tests that protect:
- regression-prone behavior;
- stable contracts;
- previously uncovered required behavior;
- high-risk algorithmic behavior;
- replaceable implementation boundaries.

Prefer existing tests when they already validate the required behavior.

Prefer shared contract tests, parameterized tests, or a common evaluation
harness for replaceable implementations instead of duplicating nearly
identical test suites.

Validation that uses existing tests, linting, type checking, compilation,
or an existing benchmark MAY be included as part of the implementation
task rather than becoming a separate task.

### Phase Discipline

Preserve user-story organization required by this workflow.

However, do NOT create artificial tasks solely to populate:
- Setup;
- Foundational;
- individual architectural layers;
- Polish or cross-cutting phases.

Create Setup tasks only when actual setup work is required.

Create Foundational tasks only when there is a genuine shared blocking
dependency needed by multiple user stories.

Create Polish or cross-cutting tasks only when independently necessary
work remains after the user stories are complete.

Do not duplicate work between Setup, Foundational, User Story, and Polish
phases.

### Scope Discipline

Do not include unrelated cleanup.

Do not introduce adjacent improvements merely because they are convenient.

Do not solve speculative future problems.

Do not create infrastructure or abstractions unless required by the
implementation plan or project constitution.

Every task MUST answer:

"What meaningful state of the system becomes true when this task is
finished?"

If a proposed task cannot answer this question with a meaningful
engineering outcome, merge it into a related task or remove it.


### Checklist Format (REQUIRED)

Every task MUST strictly follow this format:

```text
- [ ] [TaskID] [P?] [Story?] Description with file path
```

**Format Components**:

1. **Checkbox**: ALWAYS start with `- [ ]` (markdown checkbox)
2. **Task ID**: Sequential number (T001, T002, T003...) in execution order
3. **[P] marker**: Include ONLY if task is parallelizable (different files, no dependencies on incomplete tasks)
4. **[Story] label**: REQUIRED for user story phase tasks only
   - Format: [US1], [US2], [US3], etc. (maps to user stories from spec.md)
   - Setup phase: NO story label
   - Foundational phase: NO story label  
   - User Story phases: MUST have story label
   - Polish phase: NO story label
5. **Description**: Clear action with exact file path

**Examples**:

- ✅ CORRECT: `- [ ] T001 Create project structure per implementation plan`
- ✅ CORRECT: `- [ ] T005 [P] Implement authentication middleware in src/middleware/auth.py`
- ✅ CORRECT: `- [ ] T012 [P] [US1] Create User model in src/models/user.py`
- ✅ CORRECT: `- [ ] T014 [US1] Implement UserService in src/services/user_service.py`
- ❌ WRONG: `- [ ] Create User model` (missing ID and Story label)
- ❌ WRONG: `T001 [US1] Create model` (missing checkbox)
- ❌ WRONG: `- [ ] [US1] Create User model` (missing Task ID)
- ❌ WRONG: `- [ ] T001 [US1] Create model` (missing file path)

### Task Organization

1. **From User Stories (spec.md)** - PRIMARY ORGANIZATION:
   - Each user story (P1, P2, P3...) gets its own phase
   - Map all related components to their story:
     - Models needed for that story
     - Services needed for that story
     - Interfaces/UI needed for that story
     - If tests requested: Tests specific to that story
   - Mark story dependencies (most stories should be independent)

2. **From Contracts**:
   - Map each interface contract → to the user story it serves
   - If tests requested: Each interface contract → contract test task [P] before implementation in that story's phase

3. **From Data Model**:
   - Map each entity to the user story(ies) that need it
   - If entity serves multiple stories: Put in earliest story or Setup phase
   - Relationships → service layer tasks in appropriate story phase

4. **From Setup/Infrastructure**:
   - Shared infrastructure → Setup phase (Phase 1)
   - Foundational/blocking tasks → Foundational phase (Phase 2)
   - Story-specific setup → within that story's phase

### Phase Structure

- **Phase 1**: Setup (project initialization)
- **Phase 2**: Foundational (blocking prerequisites - MUST complete before user stories)
- **Phase 3+**: User Stories in priority order (P1, P2, P3...)
  - Within each story: organize work by dependency order and meaningful
engineering outcomes. Tests, models, services, endpoints, and integration
do NOT require separate tasks when they form one coherent implementation
outcome.
  - Each phase should be a complete, independently testable increment
- **Final Phase**: Polish & Cross-Cutting Concerns
