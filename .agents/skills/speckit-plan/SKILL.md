## Phases

### Phase 0: Outline & Research

1. **Extract unknowns from Technical Context** above:
   - For each NEEDS CLARIFICATION → research task
   - For each dependency → best practices task
   - For each integration → patterns task

2. **Generate and dispatch research agents**:

   ```text
   For each unknown in Technical Context:
     Task: "Research {unknown} for {feature context}"
   For each technology choice:
     Task: "Find best practices for {tech} in {domain}"
   ```

3. **Consolidate findings** in `research.md` using format:
   - Decision: [what was chosen]
   - Rationale: [why chosen]
   - Alternatives considered: [what else evaluated]

**Output**: research.md with all NEEDS CLARIFICATION resolved

### Phase 1: Design & Contracts

**Prerequisites:** `research.md` complete

1. **Extract entities from feature spec** → `data-model.md`:
   - Entity name, fields, relationships
   - Validation rules from requirements
   - State transitions if applicable

2. **Define interface contracts** (if project has external interfaces) → `/contracts/`:
   - Identify what interfaces the project exposes to users or other systems
   - Document the contract format appropriate for the project type
   - Examples: public APIs for libraries, command schemas for CLI tools, endpoints for web services, grammars for parsers, UI contracts for applications
   - Skip if project is purely internal (build scripts, one-off tools, etc.)

3. **Create quickstart validation guide** → `quickstart.md`:
   - Document runnable validation scenarios that prove the feature works end-to-end
   - Include prerequisites, setup commands, test/run commands, and expected outcomes
   - Use links or references to contracts and data model details instead of duplicating them
   - Do not include full implementation code, model/service/controller bodies, migrations, or complete test suites
   - Keep this artifact as a validation/run guide; implementation details belong in `tasks.md` and the implementation phase

**Output**: data-model.md, /contracts/*, quickstart.md

### Lean Architecture Rules

- Design around known axes of change rather than maximizing abstraction or modularity.

- Before introducing an architectural boundary or abstraction, identify the concrete reason the boundary is needed.

- Consider an abstraction justified when it provides at least one concrete benefit:
  - Algorithm substitution
  - Model substitution
  - Experimentation
  - Isolation of volatile dependencies
  - Independent evolution
  - Meaningful independent validation
  - Reduced coupling across a known change boundary

- For components that are known or reasonably expected to have multiple implementations:
  1. Define a small and stable contract.
  2. Keep implementation-specific details behind that contract.
  3. Ensure callers depend on the contract rather than a concrete implementation.
  4. Prefer configuration-driven implementation selection when practical.
  5. Keep implementation-specific configuration namespaced to that implementation.
  6. Keep shared evaluation and benchmarking independent from individual implementations.

- Prefer the smallest architecture that preserves currently known variation points.

- Prefer simple composition over framework-building.

- Do NOT introduce abstractions solely for hypothetical future reuse.

- Do NOT create an interface for every class.

- Do NOT introduce factories, registries, adapters, wrappers, or plugin systems when direct construction is sufficient and no actual replacement boundary exists.

- Do NOT split a cohesive component merely to increase the number of modules.

- When planning a new abstraction, explicitly answer:
  - What is expected to vary?
  - What is expected to remain stable?
  - What contract separates the stable and variable parts?
  - How can an alternative implementation be substituted?
  - How will implementations be compared, validated, or evaluated?

- If the questions above cannot be answered with a concrete current or reasonably expected need, reconsider whether the abstraction is necessary.

- For algorithmic or experimental components with multiple expected implementations:
  - Define a shared input contract.
  - Define a shared output contract.
  - Define lifecycle expectations when relevant.
  - Define configuration boundaries.
  - Define failure and error behavior.
  - Define a shared evaluation contract.
  - Alternative implementations SHOULD normally be selectable without changing unrelated application logic.
  - Alternative implementations SHOULD be runnable against the same evaluation or benchmark harness.

- Preserve existing project architecture when it already provides an adequate boundary. Do not redesign working areas solely to conform to these rules.

- Keep architecture decisions proportional to the scope and risk of the requested change. Avoid unrelated architectural cleanup.
